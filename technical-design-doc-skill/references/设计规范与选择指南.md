# 技术设计文档模板与使用指南

> 目的：提供一套可按团队规模、需求复杂度和风险等级裁剪的通用技术设计规范，并附上可直接交给 AI 编程助手使用的提示词。
>
> 核心原则：**统一规范，按需裁剪；风险越高，设计越深入；不为填模板而写文档。**

## 1. 如何理解这套模板

这不是某一家大厂的官方模板，也不存在适用于所有公司的唯一行业标准。它是一套通用母版，可按团队研发流程调整。

- **母版**：包含常见设计章节、章节适用条件和质量检查项。
- **轻量版**：适合简单、低风险的小需求，只保留必要章节。
- **标准版**：适合大多数业务开发，覆盖总体设计、实现逻辑、数据与接口、异常和测试。
- **专项/完整版**：适合 MQ、数据同步、数据库迁移、核心链路、高并发等风险较高的需求，补充可靠性、容量、安全、发布回滚等设计。
- **团队规模不是唯一判断条件**：大厂不代表每个需求都要写长文档；小团队遇到高风险变更，也应采用完整设计。

## 2. 选择流程：先判断是否需要，以及需要多深

### 2.1 第一步：判断文档形式

| 任务类型 | 建议产物 |
|---|---|
| 极简单、低风险的局部修改，例如文案或不影响契约的简单校验 | 可使用需求单/PR 描述，不一定单独写技术设计文档 |
| 普通功能、CRUD、多个方法协作 | 轻量或标准《技术设计文档》 |
| 涉及多个模块、表结构、接口契约、跨系统协作 | 标准《技术设计文档》 |
| MQ、定时任务、增量同步、批量处理、数据迁移、并发一致性 | 《专项技术设计文档》或完整技术设计文档中的专项章节 |
| 存在多个重要技术选项，且决策影响长期演进 | 增加 ADR《技术决策记录》 |
| 主要目标是定义 API 契约 | 可单独维护《接口设计文档》，并关联总体技术设计 |
| 开发完成、交接测试 | 使用《提测说明》，不要用技术设计文档替代 |
| 生产发布步骤复杂或回滚风险高 | 增加《发布与回滚方案》 |

### 2.2 第二步：按复杂度和风险选档

| 级别 | 适用条件 | 文档深度 |
|---|---|---|
| **L1 轻量版** | 影响范围小、逻辑简单、无高风险数据操作、易验证和回滚 | 背景与目标、方案、关键逻辑、必要的数据/接口说明、测试范围 |
| **L2 标准版** | 普通业务功能；涉及多个类/模块、数据库或接口变化 | L1 内容 + 总体流程、模块职责、异常处理、事务/幂等（适用时）、配置变更、测试场景 |
| **L3 专项/完整版** | 跨系统、MQ、数据同步、数据迁移、并发/一致性、核心链路、高负载或难回滚变更 | L2 内容 + 方案取舍、失败恢复、容量/性能、安全、监控告警、发布灰度和回滚、风险清单 |

**升级规则：**只要命中高风险条件，就不能因为团队规模小而省略相关设计。风险判断优先于页数和组织规模。

### 2.3 高风险判断清单

以下任一项成立时，至少使用 L2；多项成立或影响生产数据/跨系统一致性时，通常使用 L3：

- [ ] 涉及多个系统或团队，存在外部依赖
- [ ] 新增或修改 MQ 消息、定时任务、批处理、增量同步
- [ ] 涉及事务边界、并发写入、幂等、顺序或一致性
- [ ] 涉及大表、索引、锁、批量更新或历史数据迁移
- [ ] 失败后可能丢数据、重复处理、产生脏数据或难以补偿
- [ ] 影响核心业务链路、可用性、性能或安全
- [ ] 发布/回滚步骤复杂，或数据库变更无法简单逆转
- [ ] 方案存在明显取舍，需要技术评审或长期追溯

## 3. 标题与文件命名规范

### 3.1 推荐标题格式

`《业务/模块名称 + 需求/变更主题 + 文档类型》`

示例：

- `订单管理功能技术设计文档.md`
- `上游基础数据 MQ 同步技术设计文档.md`
- `基础数据增量同步专项设计文档.md`
- `基础数据同步接口设计文档.md`
- `历史数据迁移与回滚方案.md`
- `基础数据查询性能优化技术设计文档.md`
- `ADR-001-基础数据增量识别机制选型.md`
- `基础数据同步功能提测说明.md`

### 3.2 文档类型怎么选

- **技术方案设计**：侧重问题、方案思路、备选方案和整体取舍。
- **技术设计文档**：覆盖从总体方案到具体实现的完整设计，适合作为默认文档名称。
- **详细设计文档**：侧重类/模块职责、数据结构、处理步骤、异常和实现约束。
- **接口设计文档**：侧重 API 契约、参数、响应、错误码、鉴权和兼容性。
- **数据库设计文档**：侧重表结构、字段、索引、约束、迁移和数据兼容。
- **专项设计文档**：针对 MQ、同步、迁移、性能等复杂专题。
- **ADR 技术决策记录**：记录一个重要决策的背景、备选项、结论及后果，不代替完整技术设计。
- **提测说明**：面向测试交接，写测试范围、场景、注意事项和验证方法。

通常优先使用《技术设计文档》作为主文档。只有内容需要独立维护、多人协作或被多个文档复用时，再拆分专项文档。

## 4. 母版章节与填写规则

标记说明：

- **必填**：每份技术设计都应说明；简单需求可合并为短段落。
- **按需填写**：只有涉及该主题时才保留，不涉及就删除章节，不要留下空标题。
- **高风险必填**：当需求涉及相应风险时必须说明。

| 章节 | 要求 | 说明 |
|---|---|---|
| 1. 文档信息 | 必填 | 文档版本、系统/模块、需求、作者、日期、状态 |
| 2. 需求背景与目标 | 必填 | 现状问题、目标、范围、非目标、约束和假设 |
| 3. 总体设计 | 必填 | 设计思路、模块关系、核心流程；简单需求可用文字描述 |
| 4. 详细设计 | 必填 | 核心逻辑、模块/类职责、关键规则和处理顺序 |
| 5. 数据库设计 | 按需填写 | 表结构、DDL、索引、约束、迁移、兼容与数据校验 |
| 6. 接口设计 | 按需填写 | API/MQ/第三方契约、参数、响应、错误码、鉴权与兼容 |
| 7. 异常处理与可靠性 | 必填；按场景深入 | 业务异常、失败处理；MQ/同步场景补充幂等、重试、补偿、死信等 |
| 8. 安全与性能 | 按需/高风险必填 | 权限、敏感信息、SQL 安全、容量、并发、性能指标 |
| 9. 配置与依赖变更 | 按需填写 | 配置项、定时任务、消息主题、外部依赖、开关 |
| 10. 测试设计 | 必填 | 正常、异常、边界、回归；高风险场景增加恢复验证 |
| 11. 发布与回滚 | 生产变更按需；高风险必填 | 发布顺序、验证、灰度、回滚限制、数据恢复 |
| 12. 风险与待确认事项 | 必填 | 未决问题、风险、影响和跟进人；无则写“暂无” |
| 13. 评审与变更记录 | 按需填写 | 评审结论和重要修改记录 |
| 14. 相关文档 | 按需填写 | 需求、接口、测试、ADR 等链接 |

## 6. 常见专项补充项

### 6.1 MQ / 消息驱动
至少补充：

- 生产者触发条件、消息格式、事件类型、消息唯一标识和版本
- 投递可靠性、重复投递、消费幂等、顺序要求
- 消费事务边界、ACK 时机、重试策略、重试耗尽和死信处理
- 消费失败记录、人工重放、补偿机制和数据对账
- 消息积压监控、告警阈值、扩容方式和排障流程
- 消息兼容策略、敏感数据和权限控制

### 6.2 定时任务 / 增量同步
至少补充：

- 增量识别依据、时间字段精度、边界条件和首次同步策略
- 分页/游标、断点续跑、扫描窗口和并发执行控制
- 新增、修改、软删除的识别规则
- 重复处理、漏数、乱序、延迟数据和补数方案
- 全量与增量切换、对账方式、失败重跑和运行指标

### 6.3 数据库变更 / 数据迁移
至少补充：

- 数据规模估算、执行时长、锁影响和索引策略
- DDL/DML 执行顺序、批次大小、事务边界
- 新旧代码兼容及发布先后顺序
- 迁移前备份、迁移后校验、失败续跑和回滚限制
- 大表操作、主从延迟、线上流量影响及观察指标

### 6.4 第三方接口
至少补充：

- 请求/响应契约、鉴权和敏感信息处理
- 连接/读取超时、重试条件、幂等性和限流
- 对方不可用、返回异常、字段变更和版本兼容
- 调用日志、告警、降级及人工补偿方式

### 6.5 性能优化
至少补充：

- 优化前基线和瓶颈证据
- 目标指标及测量方式
- 方案对比和副作用
- 压测数据、容量估算、回归风险和上线观察计划

## 7. AI 提示词：自动选择并使用模板

### 7.1 主提示词（建议作为全局规则）

将以下提示词配置到 AI 编程助手的全局规则或团队指令中。它的职责是**决定何时需要设计文档、选择什么深度、如何使用母版**，而不是要求每次对话都生成文档。

```text
你是一名资深 Java 后端工程师和技术设计评审人员。请根据当前任务判断是否需要技术设计文档，并按需使用《技术设计文档模板与使用指南》中的母版。

【选择原则】
1. 不要默认每个任务都生成完整技术设计文档。
2. 极简单、低风险、局部修改：若没有跨模块、数据库结构、接口契约或可靠性影响，可直接实现或给出简短方案，无需单独生成文档。
3. 普通功能：选择 L1 轻量版或 L2 标准版。
4. 涉及多个模块、数据库/接口变更、跨系统交互：至少选择 L2。
5. 涉及 MQ、定时任务、增量同步、批量处理、事务一致性、并发、数据迁移、核心链路、性能或安全风险：选择 L3 或补充对应专项章节。
6. 选择深度时以复杂度和风险为准，不要单纯根据“大厂/中厂/小厂”决定。

【文档使用规则】
1. 标题采用“业务/模块 + 需求/变更主题 + 文档类型”。默认名称为《xxx 技术设计文档》；接口、数据库、MQ、迁移、提测等内容只有在需要独立维护时才拆分成专项文档。
2. 先阅读现有需求、代码、表结构、接口契约和项目约定；不得臆造系统现状、字段、接口、性能指标或业务规则。
3. 必填章节必须说明清楚；条件章节仅在适用时保留。不适用的章节直接删除，不要留下空标题，也不要为了填满模板制造内容。
4. 设计文档应说明：背景与目标、范围、总体方案、核心流程、模块职责、关键数据/接口变化、异常处理、测试范围和风险。
5. 对适用的高风险场景，明确事务边界、幂等、并发、超时、重试、失败恢复、监控、发布与回滚；不能只写“做好异常处理”等空泛表述。
6. 如果存在多种方案且选择会影响成本、可靠性或长期演进，简要比较备选方案、取舍和选择理由；重大长期决策可建议记录 ADR。
7. 文档中的待确认信息明确标记为“待确认”，并列出需要谁确认的问题；不得用猜测填补缺失信息。
8. 文档深度应与任务相称，优先简洁、可执行、可评审、可验证。避免重复描述、空泛术语和不必要的架构设计。
9. 如果当前环境无法读取模板文件，先使用以上规则生成合适结构，并明确说明缺少模板原文，不要声称已读取。

【输出流程】
A. 先给出判断：是否需要文档、建议级别（L1/L2/L3）、选择原因。
```

## 8. 使用方式建议

### 方式 A：个人使用

将本文件放在项目文档目录或 AI 工具可读取的位置。每次复杂需求开始时，引用母版并使用“按需生成文档提示词”。

### 方式 B：团队使用

1. 将本文件作为团队的通用设计规范。
2. 将“7.1 主提示词”加入团队 AI 规则或代码助手指令。
3. 按项目情况把母版存放在固定位置，例如 `docs/standards/technical-design-template.md`。
4. 需求单中增加“设计级别：L1/L2/L3”和“设计文档链接”字段。
5. 评审时按风险清单检查，不要求所有需求都填写全部章节。
6. 发生重大实现变化时同步更新设计文档，避免文档与代码长期不一致。

### 方式 C：AI 无法自动读取文件时

不要假设 AI 已经加载了本文件。应在任务中明确提供文件内容/路径，或将“7.1 主提示词”配置到全局规则中。如果工具无法访问文件路径，就把相关模板或提示词直接粘贴进对话。

- [ ] 目标、范围和非目标明确

- [ ] 已删除不适用的空章节
