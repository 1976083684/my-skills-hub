# 测试充分性评分规则

评分是对已确认测试范围和现有证据的辅助评估，不能证明没有其他缺陷。项目已有评分规则时优先采用并注明口径；以下为默认规则，不是通用行业标准。

## 评分前提

先确认测试范围、需求或验收依据、核心场景、执行状态和证据，再评分。正常、异常、边界等维度需按业务规则设计足够的用例，不以“每维度一条”作为充分性标准。

- 尚未执行：`未评分（尚未执行）`。
- 范围或关键执行证据缺失，无法确认结果：`未评分（证据不足）`，列明缺失项，结论为“待验证”，不能默认通过或判定功能失败。
- 有可核实的结果，且已知未执行、阻塞或未覆盖项已列明：可按明确范围评分，同时保留相应风险和验收限制。
- 只对可核实的场景标记通过。Mock 仓储断言不等于真实落库；Mock 事务不等于回滚验证；顺序重名请求不等于并发或幂等验证；代码阅读与注释不等于运行证据或需求确认。

## 分级与计算

| 级别 | 判定依据 | 扣分 |
|---|---|---:|
| 错误 | 本次范围内已验证的用例失败、行为不符合契约、数据错误，或阻断测试执行的构建失败等 | 10/项 |
| 警告 | 必需验证项未执行、阻塞、缺少有效断言或证据，包括尚未验证的关键校验、事务、并发等风险 | 2/项 |
| 建议 | 不影响既定验收条件的测试维护或文档可复现性改进 | 1/项 |

`得分 = max(0, 100 - 10 × 错误数 - 2 × 警告数 - 建议数)`。

- 每项问题有唯一编号、对应场景、影响和依据，同一根因按最高适用级别扣一次，不按文件数或重复出现次数扣分。
- 只统计本轮评估时尚未解决的问题；修复后的错误须有回归证据才能关闭，另保留历史缺陷记录。
- 问题不在本次范围内、属于已确认的预期行为，或确实不适用：不扣分，必要时放在范围说明中。接受风险不等于已经验证通过。
- 缺少证据的“已通过”先改为未验证，不直接指控测试造假；关键证据不足时按上述规则暂不评分。
- 保留问题数、扣分明细和完整算式。例如 0 错误、3 警告、3 建议为 `100 - 0 - 6 - 3 = 91`。
- 100 分仅表示当前范围和证据下未识别出扣分项，不代表完整覆盖或无缺陷。不额外设置分数放行阈值。

## 评分与验收分开

验收结论依据项目约定标准、关键用例、开放缺陷和残余风险：

- 核心用例未执行或证据不足：说明“待验证”，不能因分数高而通过。
- 存在阻断验收的失败或缺陷：不通过；构建或环境阻塞时说明测试被阻塞，避免推断业务功能失败。
- 核心验收条件满足，仅有不阻断验收的遗留问题：可建议有条件通过，写明限制、处理计划和需确认的风险。未获得的人工确认不得写成已确认。
- 满足既定验收条件且没有阻断项：可通过，仍披露已知限制。

通过率另按原技能规则统计，不能用分数替代。对构建成功、单元测试、接口测试、集成测试、界面测试分别注明证据层级；按实际需求选用，不由“是否有前端改动”决定。
