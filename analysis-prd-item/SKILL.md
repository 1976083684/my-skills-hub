# 业务概念笔记（术语与模块）

## 输出目标

让第一次接触业务的人先看懂“谁遇到了什么问题、做了什么、结果怎样”，再准确理解术语，避免只背定义或被类比误导。默认使用简体中文。

## 开始前

- 先阅读目标笔记、用户指定资料及与本次概念直接相关的 PRD 或原型内容。已有解析可作线索，但不能声称读过未实际读取的原始资料。
- 用户指定文件时原地更新；未指定目标且无法从当前上下文确定时，先解释内容，再询问保存位置，不猜测文件。
- 延续原文标题、编号和案例背景。只修改本次涉及的知识点，保留用户已删改的成果。
- 区分新增独立术语与补充已有概念：能回答原章节内某个问题的追问，融入对应位置；只有需要独立解释的概念才新建术语章节。

## 单个术语的推荐结构

按以下阅读顺序组织，标题措辞自然，不要求每个术语机械套满所有小节。故事、定义和易错边界是核心；其余按复杂度取舍。

```markdown
## 序号、什么是〈术语〉？

### 1. 先看故事：〈一个具体业务问题〉
〈人物或企业、业务目标、发生的事、操作、结果。必要时配小表格或计算。〉

### 2. 再给定义：〈术语〉是什么？
〈先用一句准确的话定义，再把故事中的动作或对象对应回来。〉

### 3. 为什么需要它／它怎样运作？
〈解释业务原因、关键步骤或分类，仅保留有助于理解的内容。〉

### 4. 补上边界：〈最容易误解的问题〉
〈用正反场景、对比表或短段落澄清适用条件和例外。〉

### 5. 联系 PRD：〈它在系统中对应什么〉
〈资料确有对应关系时，说明功能、数据或上下游；没有则省略。〉

**记住一句话：〈准确且容易记住的核心含义〉。**
```

- 每个术语先讲故事，不在前面堆放大词汇表或长篇定义。
- 相关术语优先共用一个企业、产品和业务链路，让读者可以接着理解；不相关概念不强行串联。
- 不默认添加篇末“把多个术语连起来”“参考资料与使用范围”、写作方法论或全篇重复总结。确有必要的来源、适用条件与待确认信息，就近简短注明；用户另有要求时按要求处理。

## 模块/功能点也按同一标准

功能模块（界面 TAB、菜单、子系统）与术语同等对待：每个模块独立成节，沿用「先看故事 → 再给职责 → 补上边界 → 联系 PRD → 记住一句话」的阅读顺序，不用一张大表概括所有模块就完事。差异只在写法：

- 故事写成“谁在什么场景打开这个功能、做了什么操作、看到或产出了什么数据”，可以直接用具体案例数据举例；数字必须能算对，并与笔记其他章节的案例口径衔接。
- “定义”换成“它管什么”：一句话说清模块职责，加上它在业务链路中的位置（输入从哪来、输出给谁）。
- “边界”优先写与相邻模块的分工（容易混淆的，如“报核数据 vs 正式报核”）、本期范围限制（如“本期不做”）和常见误用。
- 结构相同、仅数据源不同的兄弟模块可以合写一节，但必须点明覆盖了哪几个入口、差异在哪。
- 术语章节与模块章节分开、互相引用而非重复：概念解释放术语节，模块节只讲“这个功能在链路里干什么”，涉及概念处一句话回扣并指向术语节。

## 故事怎样写

- 从具体困惑出发，例如“一批料进口时为什么可以暂不交税”，而不是先介绍行业宏观背景。
- 先用最少假设讲通正常主线，再增加一两个能揭示边界的变化：数量对不上、订单取消、来源混合等。不要让第一个案例就塞满全部例外。
- 假设企业与数字须明确为教学示例；不编造真实企业成本、税率、规模或政策效果。
- 涉及数量时写清对象、单位、期间及关键假设；检查算术、数量平衡和计量维度。成品数量不能直接减料件数量，除非已说明一对一关系。
- 类比应辅助理解，随后指出必要的失效边界；不能把“挂账”“信用卡”等类比当作法律、财务或系统机制的真实定义。
- 故事结束后点出它说明的业务含义，避免只留一个热闹情节。

## 定义与细节怎样写

- 定义先讲本质，再解释分类、角色、流程或计算，不以另一个陌生术语解释陌生术语。
- 新出现的术语就近用一句白话说明；不为解释一个词无限展开其他词。
- 细节围绕实际误解组织，优先解释“哪些算、哪些不算、什么条件下成立、与相近概念有什么区别”。不堆“细节1、细节2”的零散问答。
- 区分业务制度、产品规则和教学简化。PRD 是本项目设计依据，不能自动充当通用法规依据；产品功能不能反过来定义业务概念。
- 涉及税费时区分采购、进口、内销、出口等环节及税种；不把“免税、保税、退税”混写。货物来源、产地和保税身份也不能相互替代。
- 比例或公式必须说明计算对象、分母、单位和成立条件，不能把某种材料的比例直接当作整个产品的比例。
- 期限、税率、监管代码及处罚等强结论需有可核对依据；缺少依据时明确局部待确认，不编造结论，也不以大量免责声明淹没主体。
- 资料冲突时就近标注“待确认”和影响，不擅自选择其中一个作为确定规则。不把原型示例视作已实现行为。

## 怎样吸收后续追问

1. 提取追问暴露的知识缺口，例如“材料来自国内还是境外”背后可能是“采购来源与保税身份的区别”。
2. 将稳定的结论整理进原章节：影响主线理解的内容补到故事或定义；例外放到边界；计算问题补一个小例子；系统口径放到 PRD 对应部分。
3. 不原样追加聊天记录、“用户问／答”或重复结论。同一知识点保留一处主解释，其他位置简短关联即可。
4. 对现有内容有影响时同步纠正相关句子，避免新段落与原定义冲突；不顺便扩写未被要求的新术语。

## 完成前检查

- 新人能否仅凭故事理解业务动机、行为与结果？定义是否能回扣故事？
- 简化假设是否清楚，边界是否阻止最可能的误解，是否出现不必要的绝对说法？
- 数字、单位、比例和公式是否一致？资料中的待确认规则是否被误写成事实？
- 本次补充是否已融入合适位置，是否保留用户删改、避免重复和无关扩写？
- 模块章节是否逐个说清职责、链路位置与相邻模块分工？模块故事的案例数字是否与术语章节口径一致、能算对？
- Markdown 标题层级、表格、代码块和实际使用的本地引用是否正常？

交付时简要说明新增或调整了什么、实际检查了什么及重要未确认项；提供目标文件链接，不在回复中重复整篇笔记。纯咨询且未要求保存时，直接按上述思路回答，不擅自修改文件。
