# 技术设计文档提示词模板

## 1. 全局规则提示词（短版）

```text
请根据任务复杂度和风险决定是否需要技术设计文档，不要要求每个任务都生成完整文档。
- 极简单、低风险的局部修改：无需单独生成长文档，简要说明实现思路即可。
- 普通功能：选择 L1 轻量版或 L2 标准版。
- 多模块、数据库结构、接口契约或跨系统交互：至少 L2。
- MQ、定时任务、增量同步、批处理、并发一致性、数据迁移、核心链路、性能/安全风险或难回滚变更：选择 L3 或补充专项设计。
优先读取项目内的技术设计规范和模板；如果能访问 Skill 资源，使用 technical-design-doc-assistant Skill。只保留适用章节，不留空标题。不得臆造代码、字段、接口或业务规则；未知信息标记为待确认。输出应简洁、可执行、可评审、可验证。
```

## 2. 生成技术设计文档

```text
请基于当前需求和项目现状，使用技术设计文档规范生成一份可直接保存为 Markdown 的文档。

先判断文档类型和级别（L1 轻量 / L2 标准 / L3 专项），简述判断理由，并给出建议文件名。然后按级别裁剪模板。

要求：
- 优先检查现有代码、表结构、接口契约和项目约定；不得臆造事实。
- 覆盖背景目标、范围、总体方案、核心流程、模块职责、数据/接口变化、异常处理和测试范围。
- 涉及 MQ、定时任务、增量同步、事务、并发、数据迁移时，补充对应专项设计。
- 关键方案说明选择理由和风险；必要时比较备选方案。
- 未知信息标记为“待确认”，列出关键问题。
- 删除不适用章节，不要为填满模板而写空话。

需求：
{{粘贴需求}}
```

## 3. 评审技术设计文档

```text
请从资深后端工程师和技术评审人的角度评审以下设计文档。重点检查设计正确性和闭环，不要只做文字润色。

检查：
1. 目标、范围、非目标和验收标准是否明确；
2. 总体方案、流程、模块职责是否闭环；
3. 数据库、接口、消息契约是否完整且兼容；
4. 事务、幂等、并发、超时、重试、补偿和恢复是否按场景设计；
5. 安全、性能、测试、监控、发布和回滚是否覆盖必要风险；
6. 是否存在臆造信息、前后矛盾、模糊表述或不可验证的结论；
7. 文档深度是否与风险匹配，是否有不必要的复杂设计。

按“问题等级（阻塞/重要/一般）—位置—问题—风险—修改建议”输出，并给出是否建议通过评审的结论。

文档：
{{粘贴文档或提供文件}}
```

## 4. 编码前设计确认

```text
在开始编码前，请先阅读需求和现有代码，判断是否需要技术设计。

若需要：
1. 选择 L1/L2/L3 并说明理由；
2. 说明影响模块、核心实现方案、数据库/接口变更、异常与测试要点；
3. 优先复用现有实现，避免无必要重构；
4. 如果会改变已有公共行为、已有表结构或他人维护的代码，先指出影响和原因；关键不确定项先询问确认；
5. 对高风险场景补充幂等、事务、并发、重试、恢复、监控及回滚。

若任务简单且低风险，只输出简短实现思路，不要强行生成完整文档。
```

## 5. 将现有设计精简为适用版本

```text
请把当前技术设计文档调整为与本次需求风险相匹配的版本。
先判断 L1/L2/L3，保留必须章节，删除不适用或重复章节。不要删除与数据一致性、安全、恢复或上线风险直接相关的必要设计。列出删除/合并的章节及原因，然后输出完整修订版 Markdown。
```
