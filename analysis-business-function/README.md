# analysis-business-function

从现有系统页面、源码、接口、数据库结构、测试和项目文档出发，按四个维度理解业务的 Agent Skill：

1. **我是谁：系统定位**
2. **为谁做：用户与协作对象**
3. **做什么：业务范围与能力**
4. **怎么做：业务流程与模块协作**

## 适用场景

- 理解陌生系统解决什么问题、在业务链路中处于什么位置。
- 识别直接用户、业务参与者、上游和下游系统。
- 梳理系统承载的核心业务能力及其产出。
- 从页面或源码还原业务流程、模块职责、关键规则与数据变化。
- 将业务结论映射到实际页面、接口、方法和数据库操作。

## 使用方式

1. 将 `analysis-business-function` 目录放入所用 Agent 支持的 skills 目录。
2. 在 Agent 中启用或引用该 Skill（具体加载方式取决于所用工具）。
3. 提供系统名称、模块名称、页面、接口、源码路径或项目目录。
4. 明确本次分析边界，例如“分析订单提交流程，不分析订单后续审核”。
5. 要求 Agent 阅读真实证据并按四个维度输出，缺少证据时标记待确认。
6. 大系统开始时可选择“一次完成”或“先总览”。先总览只写到 4.1，后续模块仅列标题；确认划分和顺序并要求继续后再展开。小模块默认直接完成，已明确选择时不重复询问。

## 设计原则

- 从整体定位到用户，再到业务能力，最后到流程和模块协作。
- 先总览模式限制实际扫描深度，优先核实模块边界，避免确认前做完全部详细分析；继续时复用已有证据。
- 区分“业务流程顺序”与“模块职责划分”。
- 业务语言优先，技术实现用于验证。
- 固定四个一级维度，内部内容按目标范围裁剪。
- 不把类名、方法名、表名当成业务解释。
- 区分已确认、推断和待确认。
- 默认只读，不修改项目代码；用户要求时可保存分析文档。
- 逐业务模块解释职责、触发、数据流、规则和结果，区分业务模块与工程模块。
- 沿业务主线排序：核心模块按流程阶段展开，随后是直接支撑模块，通用管理模块放在末尾；能力清单、模块总览和详细章节顺序对应。
- 模块复用时统一说明并引用，明确并行与分支；文档顺序不代表串行调用，排序不决定分析深度。
- 简单 CRUD 只列功能概览，有业务规则或复杂协作的功能按影响展开。
- 明确实际落库方式或未落库的数据去向，记录扫描覆盖与证据缺口。
- 表格按内容选用，通常保留 3～4 个核心列；阶段和覆盖统一说明，不固定添加使用方、证据状态或分析深度等重复列。
- 关键结论保留实际依据，推断和待确认事项就近说明；规则与数据落点按复杂度选用文字或独立简表。
- 模块小节按“先是什么 → 再列入口”展开；落库模块在职责后先给“涉及的数据表”总览（表名 + 说明 + erDiagram），字段明细按表折叠、语义分组、类型字段附枚举、难理解的业务字段行尾补示例。
- 主线内容平铺，附加阅读信息（源码依据、环节规则明细、长案例、字段明细）用 `<details>` 折叠；折叠块内只用纯 HTML 且不留空行（常见查看器遇空行即关闭 HTML 块）；Mermaid 图不折叠；参考明细用灰色边框块、注意事项用黄色警示块。
- 源码依据统一为“依据（源码参考）”折叠块，逐条 `- 名称：模块相对路径`（到文件，不带方法名、绝对路径前缀和 Markdown 链接）。
- 密集内容分段表达（`1. **标签**：` + 缩进子项），小节标题用名词式，文档不写过程元信息。
- 文档只有一个一级标题，默认名称为“{分析对象名称}业务功能分析”。
- 这是可复用的实践模板，不宣称四个维度是某项行业标准强制规定。

## 文件说明

- `SKILL.md`：技能入口、四维分析模型、执行步骤、范围约束和质量检查。
- `templates/business-function-analysis-template.md`：正式分析模板。
- `examples/example-analysis.md`：虚构订单管理系统完整分析示例，仅用于说明格式。
- `examples/overview-analysis.md`：虚构总览阶段示例，展示截至 4.1 的正文和后续模块标题。
