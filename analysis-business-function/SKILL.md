# 业务功能分析

## 1. 目标与适用范围

帮助读者理解已有系统、模块、页面、功能、API、定时任务或消息消费者。按以下四个维度组织结果：

1. **我是谁：系统定位**：解决什么问题，职责边界是什么。
2. **为谁做：用户与使用方式**：谁提出需求、谁操作系统、通过系统获得什么结果。
3. **做什么：业务范围与能力**：有哪些业务功能，产生什么结果。
4. **怎么做：业务流程与模块协作**：逐模块解释数据流转、业务规则、结果及协作。

分析以业务理解为目标，不自动扩展为架构评审、性能评估、安全审计、重构或重新设计。

## 2. 基本约束

- 先明确范围，后读取证据，再形成结论。仅分析当前目标及理解它所必需的直接关联内容。
- 默认只读，不修改、删除、提交、推送或部署项目文件。用户要求保存分析文档时，可以在指定位置新增文档；覆盖已有文件遵循用户授权。
- 业务语言优先。类、方法、表和接口用于验证结论，不能代替业务说明。
- 区分业务模块与工程模块：Maven 子模块、包、Controller、Service 等不天然等于业务模块。依据实际职责、业务入口、处理逻辑和数据对象确认边界。
- 区分业务流程与模块结构：模块清单不是流程；模块可被多个流程复用，一个步骤也可涉及多个模块。
- 重要结论必须有可追溯依据；推断、缺失或冲突在对应内容旁明确标记 `推断` 或 `待确认`。有直接证据的事实可以直接陈述，`已确认` 按需标注，不逐行重复设置证据状态列。未标记不等于已验证，名称和搜索命中只提供线索，不能证明业务行为。
- 未读取的内容不得声称已分析；未执行的流程不得声称已运行验证。静态源码不能证明线上配置、实际数据或运行结果。

## 3. 分析过程

### 3.0 开始时选择分析方式

优先遵循用户本次要求和已确认的方式，不重复询问。用户明确要求“一口气分析完”“完整分析到底”时采用完整分析；明确要求“先看模块划分”“只到 4.1”等时采用先总览模式。

“分析整个系统”只说明范围，不自动等于选择一次完成；范围完整与分阶段交付可以同时成立。

整套系统、多个业务模块、多条主线或模块边界不清时，在深入扫描之前提供一次选择；若规模未知，可先快速查看项目说明和目录以判断，不先把所有模块分析完再询问：

- **先看业务主线与模块总览（大系统推荐）**：完成前三个维度及 4.1，后续模块只生成标题，确认划分和顺序后再展开。
- **一次完成全部分析**：先建立总览，再连续完成范围内各模块及跨模块协作，不在 4.1 额外停下确认。

单一小模块、页面或边界明确的简单功能，默认直接完成，简要说明采用完整分析即可，不强制增加选择环节。复杂度依据业务主线和边界判断，不设置固定文件数或模块数门槛。

如支持交互提问工具，使用工具提供上述选择；否则在回复中简短询问。等待选择期间，仅可进行可复用的初步扫描。尚未收到选择时，最多交付总览草稿并停下，不能把未回复视为同意完整分析。

**先总览模式的执行边界：**
- 只做足以确认定位、用户、主要能力、主线和模块边界的扫描：项目说明、结构、入口，以及核实职责和交接所需的少量关键实现。不能提前穷尽各模块调用链、SQL、字段或异常分支，再仅隐藏输出。
- 正文分析截止 `4.1 业务主线与模块总览`。在 4.1 说明模块划分和顺序，影响理解的证据缺口就近标注；后续只生成按业务主线排序的模块标题，不填正文、子标题或空表，也不展开详细跨模块流程与最终分析结论；允许在 4.1 绘制概览级业务主线流程图。
- 区分“建议后续详细分析/概览”与“本轮实际仅做总览”。标题是计划，不能计为已分析；前三个维度也保持概览深度。
- 交付总览后停止详细分析，简短说明总览已完成及后续尚未展开，不固定罗列确认问题。用户要求调整时先修正总览；用户明确“继续”时按当前总览展开，若只指定部分模块则只展开这些模块。仅收到重命名、调序等修改意见不代表要求继续全文。
- 继续时复用已有证据、总览和标题，对修改范围及尚未读取的实现增量分析；用户已确认继续后，不逐模块重复确认。

### 3.1 确定范围与模块清单

记录分析对象、边界、证据来源和重要缺口。系统级分析先识别业务能力，再建立模块清单，不从罗列全部类或数据表开始。

分析过程中记录各模块计划深度及实际覆盖，区分 `详细分析`、`概览` 或 `范围外`。交付时统一说明共性，单独指出例外及原因，不要求每张表增加进度或深度列。用户要求完整分析时，不得自行只挑一个主流程代表全部模块；受资源或证据限制时，明确未完成项，不声称完整覆盖。

### 3.2 扫描源码并追踪实际实现

存在源码时按以下路径逐步收敛；无源码时使用可访问的页面、接口、文档等证据，并说明限制。扫描深度服从 3.0 的模式选择：先总览仅按需浅层核实，完整分析或获准继续后再逐模块详细追踪。

1. **建立全貌**：阅读项目说明、工程结构、模块说明和必要配置，识别业务范围与代码分布。
2. **发现入口**：使用 `rg --files`、`rg` 等已有搜索工具查找 HTTP 接口、定时任务、MQ 消费者，以及与目标相关的其他实际触发点。排除构建产物、第三方依赖和无关目录。
3. **归属业务模块**：结合入口、实现和数据对象归类，避免仅凭目录名划分业务。
4. **追踪实现**：从入口进入具体 Service 实现，按需要跟踪 Repository、Mapper/XML、外部调用、事件或消息。遇到多个实现、策略分发或条件配置时，核实选择条件；无法确定则标记待确认。
5. **核实业务含义**：阅读关键条件表达式、DTO 校验、枚举、计算转换、SQL 过滤及写入、异常处理。关联测试和文档可作补充；存在冲突时不静默取舍。
6. **汇总覆盖情况**：记录模块、主要入口、已追踪流程和未展开项，区分详细追踪、仅发现入口和证据缺失。

对详细分析的模块，归纳已发现的主要业务入口；普通 CRUD 可合并概览，承载业务规则或复杂协作的功能分别追踪。完整读到业务结果、关键数据落点和直接交接边界后即可停止，不递归扫描所有依赖。

边界要求：
- 接口声明不能替代实现，搜索命中不能替代阅读相关逻辑。
- 数据流必须说明数据的业务含义、关联标识、转换和去向，不能仅写 `Controller → Service → Mapper`。
- Feign 等远程调用只能确认本地请求、响应处理及失败处理；没有远端证据时，不推断远端内部规则或落库行为。
- 检查静态实现一般不需要启动应用、连接数据库或运行测试；仅在确有必要且授权范围允许时执行，并如实区分执行结果与静态结论。

### 3.3 沿业务主线确定模块顺序

根据系统定位和实际证据，先概括核心业务从触发到结果的阶段，再建立阶段与模块的对应关系。模块分析按以下顺序组织，业务能力清单、模块总览和详细章节保持对应顺序，不按目录名、字母、代码量或扫描发现顺序排列：

1. **核心业务模块**：沿业务流程阶段依次展开；流程为“1 → 2 → 3”时，相关模块按对应阶段排列。
2. **直接支撑模块**：提供基础数据、共享规则或业务查询等能力的模块，放在所支撑的核心主线之后。理解主线必需的前置条件，在首次用到时简要交代，细节留在该模块章节。
3. **通用管理模块**：用户管理、日志管理、系统配置等与当前主线关联较弱的能力，放在模块分析末尾。

分类取决于当前系统的业务定位，不能只凭名称判断；例如用户管理在身份管理系统中可能就是核心业务。排序决定阅读组织，分析深度仍由业务规则和影响决定：核心流程的简单 CRUD 仍可简写，后置模块中影响主线的权限或配置规则仍需说明。

一个模块参与多个阶段时，在首次承担核心职责的位置完整说明，后续阶段引用；跨流程共享的支撑模块统一说明一次。存在并行、分支或循环时，按业务阶段分组并明确关系，不把文档顺序写成串行调用。多条独立主线按用户关注点及系统目标分别组织，说明排序依据，不强行拼成一条流程。证据不足以确认先后时，按已确认的职责分组并标注待确认，不虚构流程。

### 3.4 形成前三个维度

- **我是谁**：类型、业务问题、围绕什么业务，以及在上层业务链条中的位置。输入输出可并入业务说明，边界可并入系统位置说明，不固定拆出独立标题。系统级分析在有助理解或用户要求时，用简洁流程图标出行业或上层业务阶段与本系统承担的环节；行业简化示意与源码流程分别标注，不能把行业环节都写成本系统已实现。
- 系统位置可从业务和系统两个维度解释：前者说明在上层业务链中承担什么环节，后者说明与上下游系统的职责和交接关系。优先使用用户提供的业务与架构资料；资料中的系统名称与分析对象不一致时，明确其对应关系是否已确认，不把同类系统的能力或集团架构当作当前对象已实现的接口。未知的系统边界、交接数据和触发方式就近标注“待用户提供”及所缺信息；业务协作不等于直接调用，图中应区分。
- **为谁做**：用简表说明服务对象和直接操作人员如何参与、解决什么问题，再以用户参与流程解释“需求与资料 → 人员操作系统办理 → 业务结果 → 接收方”。相同办理过程可合并展示，保留需求来源、资料归属和结果接收者的差异。客户不天然等于系统账号用户；外部系统不作为用户混入表中，其协作在对应业务流程说明。没有实际必要时不展开岗位推测、协作系统清单或源码入口章节。
- 结合用户说明辨别开发中、试运行或已上线等产品阶段；将目标客户、拟定服务模式、现有实现和实际运营分别表达。用户明确提供的业务背景可作为依据，不再标为无来源猜测；仍不确定的目标范围保留“潜在／拟定”等表述，不推定客户门户、下单渠道、岗位权限或生产行为已存在。
- 存在客户委托、内部代办或多方服务关系，或用户要求时，在“为谁做”绘制服务关系流程图，说明需求发起方、办理方、系统操作与结果接收方。拟定模式应显式标注，未知交接用虚线或就近说明；与“怎么做”的源码业务流程图区分，避免重复技术步骤。
- **做什么**：按一致的业务粒度说明能力、解决的问题和业务结果。主要输入在模块数据流中展开；使用方通常已在“为谁做”说明，仅当能力之间的使用方差异影响理解时补充。不把业务能力与 Mapper 调用等技术动作并列。

### 3.5 逐模块分析“怎么做”

本节及后续详细分析仅用于完整分析模式，或用户确认总览并要求继续后。先总览模式在完成 3.3、3.4 后，直接按第 4 节交付总览和模块标题。

每个模块应让读者回答：**它管什么、谁来触发、数据怎么走、按什么规则处理、最终留下什么结果。** 按实际复杂度裁剪，不强制为每项建立独立章节。

| 重点 | 应解释的内容 |
|---|---|
| 职责与边界 | 解决的问题、负责的业务、交给其他模块的事项 |
| 功能与入口 | 功能清单、触发方、必要输入；用户操作、接口、定时任务、消息等 |
| 数据流转 | 数据来源、核心业务对象、关联标识、读取、转换、筛选、汇总及去向 |
| 数据落点与状态 | 是否持久化；关键表/对象、新增或更新方式、主从关联、逻辑删除、状态变化及生效条件 |
| 关键规则 | 操作前提、决策条件、计算口径、过滤、去重、字段覆盖规则及限制 |
| 协作与结果 | 直接依赖、交接的数据或结果、接收方及最终业务产出 |
| 异常与一致性 | 影响结果的重要失败、部分成功、事务范围、重复处理及实际恢复机制 |

没有落库时，明确实际行为是查询返回、计算结果、缓存、外部调用或消息发送等；若去向无法确认则说明缺口。不得为凑章节假设存在数据表。持久化只解释理解业务所需的关键对象、字段和写入语义，不输出完整数据字典。

事务、幂等、并发、重试、补偿等只在影响当前业务结果时展开；不能因存在异常就假设有回滚或补偿。

### 3.6 按业务复杂度分配深度

| 功能类型 | 分析要求 |
|---|---|
| 简单 CRUD | 功能清单、操作对象、必要限制与结果；可合并成表，不逐方法或逐字段讲解 |
| 包含业务规则 | 展开触发、关键判断、数据处理/状态变化及业务结果 |
| 跨模块、同步或异步复杂流程 | 还原端到端数据流、交接、关键分支、重要失败结果和实际恢复行为 |

判定依据是业务影响，不是代码行数或方法名称。普通 CRUD 若包含权限过滤、状态限制、关联更新、级联影响、外部通知等，应提取其中影响业务的规则分析；不要把框架通用动作当成业务规则。

### 3.7 汇总跨模块协作与证据

逐模块分析后，说明哪些模块通过调用、数据读写、事件、消息或人工操作交接，交接的内容和条件是什么。没有证据不能凭共同表名或相似名称断言协作链路。

跨模块流程统一解释一次，模块内部只描述本模块责任并引用共享流程。流程存在分支、异步或多方交接且图形有助理解时，再绘制流程图或时序图；模块关系图与流程图分别表达。

将核心业务结论映射到实际文件、符号和必要的 SQL、配置、测试或文档。位置准确即可；行号只在实际核实时填写。记录覆盖范围和待确认事项，不罗列所有文件。

## 4. 输出与标题规范

使用 [分析模板](templates/business-function-analysis-template.md)，按实际范围和模式裁剪。需要格式参考时，完整分析读取 [完整分析虚构示例](examples/example-analysis.md)，先总览读取 [总览阶段虚构示例](examples/overview-analysis.md)；不能将示例当成项目事实。

- 文档标题：`# {分析对象名称}业务功能分析`，全文只有一个一级标题。
- 保存文档时，默认文件名为 `{分析对象名称}业务功能分析.md`；用户指定名称或目录时优先遵循。未要求保存时不强制创建文件。
- 二级章节依次为：`一、我是谁：系统定位`、`二、为谁做：用户与使用方式`、`三、做什么：业务范围与能力`、`四、怎么做：业务流程与模块协作`。
- “怎么做”按“业务主线与模块总览 → 逐模块分析 → 跨模块协作流程 → 分析结论与待确认事项”组织。总览先简述核心阶段及模块对应关系；模块章节遵循 3.3 的排序规则，使用真实业务名称，编号动态递增，不固定模块数量。
- 先总览模式保留 4.1，正文到此为止，后续模块只保留真实名称的三级标题；在标题下用一条简短说明标明当前阶段及未展开状态，不单设“分析范围与依据”章节。这些计划标题是有意保留的提纲，不应补写占位正文；当前证据缺口和待确认事项放在相关结论旁或 4.1。
- 完整分析时，单模块可省略模块总览；无跨模块协作时省略对应章节。简单 CRUD 模块可仅用简表，无须展开全部子标题。前三个维度只写相关范围，不重复模块细节。
- 代码证据以“依据”形式集中放在对应小节末尾的折叠块内，逐条 `- 名称：模块相对路径`（到文件，不带方法名和绝对路径前缀，不用 Markdown 链接，详见“依据（源码参考）写法”）；不在总览、功能、规则和协作表中重复设置证据列。

### 笔记结构与流程图

- 按标准业务笔记组织，主题切换时使用有意义的小标题；不要把定义、业务主线、输入输出、职责边界堆成连续长段落，也不要只给长段落加粗开头。
- 系统定位按需组织为“是什么、解决什么问题、围绕什么业务、在上层业务中承担哪一环”；不在标题中写死主线数量。输入输出和职责边界优先并入对应业务说明，只有复杂度值得单独解释时再独立成节。
- 用户章节聚焦人或组织的参与和所得结果，产品阶段简要说明一次，不固定增设“当前阶段与目标用户”等重复章节；能力与模块清单较长时，按核心业务、直接支撑、通用管理拆表，保持同一业务顺序。并列要点用列表，每段围绕一个主题。
- 默认不输出“分析范围与依据”章节，也不换一个名称搬运整段过程汇报。必要的阶段说明用标题下一条短注，证据就近引用，重要缺口就近标注；总览不默认单设源码定位、后续展开重点或待确认事项章节。
- 用户要求开头用表格时，以精简概况表呈现产品阶段、服务对象及文档状态，不把表格扩展为过程汇报；“为谁做”以服务对象表开头。
- 系统级、多主线分析在 4.1 提供 Mermaid 概览流程图；用户要求流程图时必须提供。源码业务流程图只展示已核实的触发、业务步骤、交接和结果；基于用户说明的拟定服务关系另行标注为目标模式，多条主线可分图；节点用业务语言，条件标在连线上。
- 图中未核实的关系不画成确定箭头：可省略并说明缺口，确有必要展示的推断用虚线并明确标注。阅读顺序、模块依赖、业务执行先后不能混用。
- 概览流程图不改变总览模式边界：只画已核实的主线交接，不为补图提前深挖全部状态、SQL 或异常分支；模块关系图另行标明类型。
- 图宽控制：一个中心节点挂多个互不关联的子节点、导致图横向过宽时，按业务主题拆成多个上下排列的小图，每图前加粗体主题标签（如 `**单证主体与来源占用**`）；各组之间无连线的节点不应为凑一张图而横向排开。erDiagram 不支持 `direction` 指令，拆图是压缩宽度唯一可靠手段；flowchart 除拆图外也可用 subgraph 分组上下布局。拆分后图下的编号说明列表按图的主题顺序排列。
- Mermaid 语法硬规则（违反即渲染失败，逐图核对，不允许只凭“看起来对”交付）：
  - 节点文本一律用半角双引号包裹：`A["文本"]`、`B{"文本"}`、`C[("文本")]`；菱形、圆形节点同样适用。
  - 连线标签用管道符裸文本：`A -->|标签| B`，不加任何引号；仅虚线带标签用半角双引号：`A -. "标签" .-> B`。
  - 严禁用全角引号 `“”` 包裹任何 Mermaid 文本（节点、标签内均不是定界符，只被当普通字符，与 `：`、`，` 等混排时分词直接失败）。
  - 半角高危字符 `%` `>` `<` `,` `(` `)` `/` `=` `*` `?` 出现时必须位于半角双引号内（`%` 是注释符，最致命）；全角标点不受影响。
  - 交付前逐图过一遍 [mermaid.live](https://mermaid.live) 渲染验证；无法验证时在交付说明中如实标注“未渲染验证”。
- 更新输出结构时同步维护模板和示例，避免旧示例继续引导旧格式。

- 多条主线的关联优先放在对应流程或模块职责旁，用具体来源、交接条件和结果解释；不为“交叉与共享支撑”之类抽象概括单设标题，只有存在前文未讲清且值得集中说明的关系时才另设小节。
- 总览不固定输出源码索引、后续分析计划或问题清单。源码依据贴近结论；仅保留影响当前理解的重要未知项并就近说明，不把尚未详细分析的所有内容列为待确认问题。

### 表格与表达规范

- 表格单元格包含多个独立事项时，可用 `<br />` 换行；称谓保持简洁且一致，如“本司业务操作人员”，不因缩写改变对象含义。
- 表格用于并列比较多个对象，不要求每个章节使用表格。短说明用文字，顺序清晰的流程可用有序列表；单条信息通常不单独建表。
- 通常保留 3～4 个核心列，按实际信息增减；这不是列数上限，不能为压缩列数省略关键规则、关联标识、状态变化或数据去向。
- 删除全为空、内容重复或没有区分价值的列；少数行特有的信息就近补充。模板中的表格是可选表达方式，不要为了填满模板制造内容。
- 默认不设“使用方”“证据状态”“分析深度”“实际覆盖”等重复列。“类型”“执行方”“输入”“关键限制”等仅在对本表理解有实际帮助时增加。
- 4.1 重点呈现“模块、主线位置、主要职责、主要功能”。已按支撑模块、通用管理等分组时，单元格直接写具体业务作用，如“备案资料”，不再重复“直接支撑：”等分类前缀；整列与职责重复时合并或删除。当前阶段和覆盖范围统一说明一次；个别模块的划分疑点、建议深度或范围例外单独备注，代码位置不作为固定列。
- 业务规则与数据落点分别表达条件约束和持久化语义。复杂模块可分表说明，简单模块可用一段话合并讲清，不强制两张表；无落库时直接说明实际去向。
- 证据精简只改变呈现方式，不降低核实要求。保留核心结论依据，并在推断或待确认内容旁明确说明原因；多个重要待确认项可统一汇总，先总览模式放在相关结论旁或 4.1。

### 模块小节的展开顺序与入口写法

- 模块章（4.x）先讲“负责什么、由谁触发”，随后紧跟“涉及的数据表”小节：三列清单（表名/描述/存什么，见“数据表与字段明细”）+ erDiagram 表达表间关系；后续小节直接使用表名，不再重复解释。没有落库的模块省略该小节，改为说明实际数据去向。
- 功能小节内固定顺序：先解释“是什么、解决什么”，再列入口。单个入口一行：`入口：\`POST /order/cos/actions\` 同步提交动作`；多个入口用“入口：”引导，逐条 `- ` 列出。不在章首集中罗列 Controller 链接。
- 小节标题用名词式（“涉及的数据表”“COS 订单接入”），不用疑问句式（“如何进入”“怎样查看”）。章节级主标题（我是谁/为谁做等）保留原有设问风格。
- 编号规则列表（1. 2. 3. …）前必须有引导句，说明列表与流程图的关系（图是骨架，列表是各环节的展开），不让读者自行猜测列表用途。

### 分段表达

- 密集说明不用长段落：主点用 `1. **标签**：` 编号，多要点展开用缩进 `   - ` 子项；只有一个要点的主点一句写完，不强行拆。
- 并列规则、前提、处理动作优先分点，每点围绕一件事；解释性文字一律用分步列表或要点列表，不写大段连贯文字。

### 数据表与字段明细

- “涉及的数据表”清单固定三列：`表名 | 描述 | 存什么`。描述 = 该表的中文表名，以 DDL 表级注释（CREATE TABLE 的 COMMENT）为准；无 DDL 时依次以建表语句、实体类注释为准并标注来源；禁止凭表名语义自行概括中文名。
- 字段明细折叠块标题（`表名 — 中文名`）必须与清单“描述”列逐字一致，两处同步修改。
- 字段明细按表分块，每表一个折叠块；块内按语义分组（如“标识与来源”“状态与控制”“公共审计字段”），格式 `- \`字段名\` 中文名`。
- 类型/状态字段在中文名后附枚举取值，如：料件成品标记（1成品 2半成品 3料件 5边角料）。
- 难理解的业务字段（如成交方式、地区编码、申报海关、运输方式名称快照）行尾补 `，示例：xxx`；审计字段、已附枚举的类型字段和自明字段（电话、地址、数量、日期等）不加示例；示例不单独成 JSON 代码块。
- 字段以实体类/DDL 为准完整列出，不漏字段；表名与字段名一律转写为小写展示（代码注解或 DDL 为大写时也统一小写，方便阅读）；枚举/常量取值保持原样。

### 折叠块（details）规范

- 主线内容平铺：小节定义、主流程、流程图、结论表不折叠。附加阅读信息折叠：源码依据、各环节规则明细、长案例叙事、字段明细。定义骨架（是什么/场景/组成/输入输出）保持平铺，案例叙事折叠。
- Mermaid 图不能放进折叠块（折叠块内代码块不渲染）。
- 折叠块内不使用 Markdown 语法：常见查看器遇空行即关闭 HTML 块，导致列表、代码块跑出折叠外。块内一律用纯 HTML：`<p><strong>分组名</strong></p>`、`<ul><li><code>字段</code> 说明</li></ul>`，且块内不留空行。
- 折叠块内展示报文/JSON 案例用纯 HTML `<pre>`（不用代码围栏，否则跑出块外）；可带行尾注释并标注为示意报文（非严格 JSON）。接口入参案例按语义分组、行尾注含义，组级或块尾标注数据落点（→ 哪张表）；只列常用字段，完整定义指向接口契约与字段明细，避免与字段明细折叠块重复。
- 两种固定样式：
  - 参考明细类（默认灰色）：`<details style="border: 1px solid #ddd; border-radius: 4px; padding: 8px;"><summary><b>标题</b></summary>`
  - 注意事项类（警示黄，仅用于容易误用的约束和例外）：`<details style="border: 1px solid #f0c36d; background: #fff9e6; border-radius: 4px; padding: 8px;"><summary><b>⚠️ 注意事项</b></summary>`

### 依据（源码参考）写法

- 格式：逐条 `- 名称：src/main/java/... 模块相对路径`。只到文件，不带方法名，不带 `D:/` 等绝对路径前缀，不用 Markdown 链接。
- 依据块整体放入灰色折叠块，标题为 `<summary><b>依据（源码参考）</b></summary>`；4.1 总览中的依据同样单独成块，不与正文混排。
- 文档不写过程元信息（“已完成”“本轮未修改文件”“已验证渲染”等过程汇报），只保留业务内容本身。

## 5. 交付检查

- 已按用户选择执行；复杂系统未在模式未定或总览待确认时擅自展开详细分析，小任务和已明确的完整分析未被反复打断。
- 先总览交付仅包含截至 4.1 的概览正文与后续模块标题，已简要说明实际覆盖和未展开状态；以下涉及模块细节的检查只适用于本轮实际展开的模块。
- 已区分产品阶段、潜在服务对象与直接操作人员；服务关系图未把拟定模式写成已实现或已上线流程。
- 范围、业务模块边界和实际覆盖程度清楚；业务模块未与工程模块混淆。
- 四维结构完整，文档只有一个一级标题，章节深度与业务复杂度匹配；不同主题有清晰小标题，未堆叠长段落，未输出“分析范围与依据”章节。
- 系统级、多主线或用户要求的流程图已提供；图文一致，箭头条件与证据相符，未把阅读顺序画成确定流程。
- 每张 Mermaid 图已逐图核对语法硬规则：节点文本半角双引号、连线标签管道符裸文本、无全角引号、半角高危字符已包裹；已渲染验证或如实标注未验证。
- 表格按需使用，已删除重复、空白和无区分价值的列；阶段与覆盖统一说明，未为减少列数丢失关键业务信息。
- 已说明业务主线与模块顺序，能力清单、模块总览和详细章节相互对应；支撑和通用管理模块按关联程度后置，未把阅读顺序误写成运行依赖。
- 每个已详细分析的模块都能回答职责、触发、数据流、规则和结果五个问题。
- 已说明实际数据落点或未落库行为；关键写入方式、状态变化和生效条件有证据。
- 简单 CRUD 简写；有业务规则和跨模块影响的功能没有被当作普通 CRUD 略过。
- 模块内部流程与跨模块协作清晰，失败与一致性仅按业务影响和实际证据展开。
- 核心结论可追溯，已确认、推断和待确认可区分；未将静态分析描述成运行验证。
- 未加入无关审计或优化方案，未修改项目代码；未完成项和证据缺口如实披露。
- 模块小节按“先是什么 → 再列入口”展开，入口格式正确（单个一行、多个逐条列出），未在章首集中罗列 Controller 链接；小节标题为名词式。
- 落库模块已在职责后给出“涉及的数据表”三列总览（表名/描述/存什么 + erDiagram）；中文表名已核对 DDL 表级注释，字段折叠块标题与描述列逐字一致；字段明细按表折叠、语义分组、枚举与示例按规则取舍，字段无遗漏。
- 编号规则列表有引导句说明与流程图的关系；密集内容已分段表达，无大段连贯文字。
- 折叠块使用正确：主线内容平铺；源码依据、各环节规则明细、字段明细等附加信息一律折叠，编号规则明细列表不得平铺留在正文；案例折叠而定义骨架平铺、Mermaid 图未折叠；details 内为纯 HTML 且无空行；灰/黄两种样式按用途区分。
- 依据按“名称：模块相对路径”逐条列出并整体折叠，不含方法名、绝对路径和 Markdown 链接；文档无过程元信息。
