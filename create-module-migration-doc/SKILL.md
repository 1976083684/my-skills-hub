# 创建模块迁移清单 Skill

## 目标

在正式迁移前，盘点某个系统下指定业务模块中**需要纳入迁移范围的现有文件及资源**，生成结构统一、可评审、可追踪的 Markdown 迁移清单文档。

本 Skill 只负责迁移前的清单梳理和文档生成，不执行代码迁移，不生成迁移实现代码，也不把「迁移处理类、迁移脚本或迁移方法」误当作业务系统待迁移文件。

## 适用场景

- 用户要求梳理某个系统某个模块的待迁移文件。
- 用户提供源码目录、项目路径、文件列表或相关说明，要求生成迁移清单。
- 用户要求基于标准模板补充、修订或检查已有迁移清单。

## 输入信息

优先使用用户已提供的信息，不重复询问已明确的内容。根据实际情况收集：

- **系统名称**和**模块名称**（决定文档文件名，必须明确；可从项目名称或用户需求中推断，推断时需在交付说明中告知用户）。
- 项目根目录或源码位置。
- 迁移范围；明确不迁移的模块、目录或文件。
- 已知的迁移约束、关联系统、外部依赖。
- 编制人、评审人等文档信息；未知内容统一保留为「待填写」。

如果缺少项目源码或文件清单，不得假装已经扫描源码。应基于已提供的信息输出草稿，并明确哪些内容待补充或核实。

## 工作流程

0. **确认代码基线分支（扫描前必做）**：执行 `git fetch origin master`，用 `git rev-list --left-right --count HEAD...origin/master` 比较当前分支与最新 master。当前分支是最新 master、与之一致、或**领先于它（包含 master 全部提交，即落后数为 0）**，均可直接扫描；仅当当前分支**落后**最新 master（缺少 master 已有提交）时，必须先向用户确认是否仍以当前分支为基线扫描，得到确认后再继续；基线信息（分支名 + commit）记入文档信息。
1. **确认系统与模块**：确定系统名称和模块名称，用于文档命名。
2. **确认纳入与排除范围**：分别记录迁移范围和不迁移范围；不根据猜测扩大范围。
3. **盘点现有文件**：按项目实际文件和资源归类，记录原文件的项目全路径。
4. **判断迁移方式**：仅在有依据时标记为「迁移」「修改」或「重写」；无法判断时填「待确认」，不要擅自决定。
5. **整理关联依赖**：记录确实影响迁移完整性的依赖对象（关联表、外部接口、公共组件、配置项等），并标注是否需要同步迁移；**不确定是否迁移的对象不写入迁移范围，统一放入关联依赖并标记「待确认」**。
6. **填写验证项**：默认保留模板中的基础验证项；根据本次迁移特点可补充，不适用项说明原因。
7. **输出并检查文档**：基于模板生成 Markdown，按命名规则保存，检查路径、分类、序号、范围和待确认事项是否一致。

## 文件分类规则

模板中的文件分类是候选分类，不是必须全部保留。应按当前模块实际涉及的文件类型增删分类：

- Controller
- Service
- 数据访问及持久化
- 实体及数据模型
- 枚举及常量
- 数据库及 SQL 脚本
- 配置文件
- 工具类
- 消息及事件处理
- 接口定义及公共组件
- 参数校验及转换映射
- 异常处理及错误码
- 定时任务及后台处理
- 权限及安全处理
- 其他文件及资源

规则：

- 不存在的分类删除，不为凑齐模板而保留空分类。
- 发现实际存在且属于迁移范围的其他文件类型时，可新增分类。
- 同一文件原则上只归入一个最合适的分类，避免重复统计；确有跨类别意义时在备注中说明。
- 文件路径必须填写**项目全路径**，即从项目根目录开始的相对路径（如 `模块目录/src/main/java/.../XxxService.java`），或用户明确要求的绝对路径；不得只写文件名。
- 不得虚构文件、路径、依赖关系或验证结果。
- 仅盘点文件和资源，不把单独的方法、代码片段或迁移操作步骤当成文件条目。
- 迁移方式统一使用「迁移 / 修改 / 重写 / 待确认」；如用户要求严格使用前三项，则对无法判断的条目先留空并在备注中注明待确认。

## 输出要求

### 文档命名（强制）

- 输出文件名统一为：**`{系统名}{模块名}迁移清单.md`**
  - 示例：系统为「订单系统」、模块为「支付模块」时，文件名为 `订单系统支付模块迁移清单.md`。
  - 名称中不要使用空格、斜杠等非法文件名字符。
- 文档内一级标题与文件名一致：`# {系统名}{模块名}迁移清单`。
- 保存位置：默认保存到当前工作目录或用户指定目录；若用户未指定，输出到项目根目录或会话工作目录，并在交付时告知完整路径。

### 文档内容

- 默认输出 Markdown（`.md`）。
- 保留「文档信息、迁移范围、待迁移文件清单、关联依赖及迁移说明、迁移验证、迁移确认」六个一级章节。
- 文档信息：记录**分支名称（代码基线，分支名 + commit）**；不单列与文件名重复的「文档名称」行。
- 迁移范围：保持预览效果，分独立小表格呈现**迁移模块、功能列表、数据表、清单数量总览**四项，不混入不迁移范围、背景说明等其他内容。
- 文件清单使用表格，至少包含：序号、原文件路径（项目全路径）、迁移方式、备注；各分类标题标注数量（如「3.1 Controller（1 个）」）。
- 备注精简易懂，内容过长时用 `<br />` 分段，不写长句。
- 未知信息填写「待填写」或「待确认」，不能自行编造。
- 只输出与当前迁移对象有关的分类，删除不适用的分类。
- 保持内容简洁、可评审；不要在清单中混入迁移方案设计、代码实现、迁移后的详细操作步骤或无关描述。

## 生成后的自检

交付前逐项检查：

- [ ] 文件名符合 `{系统名}{模块名}迁移清单.md` 命名规则，文档标题与文件名一致。
- [ ] 代码基线分支已确认（不落后于最新 master，或经用户确认），并已记入文档信息。
- [ ] 迁移范围只含迁移模块、功能列表、数据表、清单数量总览；不确定是否迁移的对象均已放入关联依赖并标记待确认。
- [ ] 每个文件条目都属于本次迁移范围。
- [ ] 文件路径足够完整，能够在项目中定位。
- [ ] 不存在为填满模板而保留的空分类。
- [ ] 没有把方法、代码片段或迁移处理逻辑误列为文件。
- [ ] 迁移方式有依据；不确定项已标记待确认。
- [ ] 备注精简，过长内容已用 `<br />` 分段。
- [ ] 关联依赖和同步迁移要求清楚。
- [ ] 验证结果没有在未经验证时写成「通过」。
- [ ] 文档信息和迁移确认中的未知字段均保留待填写状态。

## 模板使用

以本 Skill 目录下的 `templates/module-migration-doc-template.md` 为基础模板。按当前模块实际情况复制并填写；不要直接覆盖原模板。
