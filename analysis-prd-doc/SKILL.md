# PRD 与原型业务解析

## 目标

让读者看懂每个模块什么时候用、用户怎么操作、系统做什么、结果去哪里；再判断整条业务是否能走通，整理可以直接向产品确认的问题。默认使用简体中文，先讲业务，再讲问题，不只复述页面、字段和按钮。

使用 [输出模板](references/output-template.md) 组织分析结果。简单模块可合并小节，复杂模块展开分支和状态；不机械凑章节，不扩展为技术设计。

## 阅读与扫描

1. 确定用户指定的 PRD、原型、附件、版本和分析范围；先查看已有笔记与相关项目约定。未指定范围时，分析所提供资料覆盖的业务模块，不自行扩展到整个系统。
2. 盘点目录、功能列表、页面、弹窗、页签、按钮及流程说明，建立模块清单。区别本期建设、既有能力、后续版本与暂不建设内容，不能把“本期不做”当成业务不需要。
3. 阅读每个模块的业务说明、字段规则、操作说明和相关原型，并回查跨模块引用。原型不只看列表主页面，还要查看相关弹窗、明细、提示及状态展示。
4. 对每个入口跟踪“触发条件 → 输入 → 校验／处理 → 输出 → 状态 → 下一步”；汇总数据来源、计算口径及上下游依赖。必要时按业务对象追踪全生命周期。
5. 用一个最小正常案例走完整条主线，再检查实际相关的异常分支。资料不足处停下来标注断点，不能用自行补全的流程证明需求闭环。

使用适合格式的现有工具读取资料；PDF 的表格、截图或页面布局影响理解时核对对应页面，不能仅凭文本提取推断。长文分段阅读，但保留覆盖清单，避免只看目录或部分页面就宣称完成全量检查。静态原型只支持判断设计描述，不能据此声称交互或后台已实现。

## 输出的证据边界

- **资料明确**：有可定位的直接说明，可在相应段落或问题中注明 PRD 章节／实际核对的页码、原型页面／弹窗等位置。
- **推测**：根据上下文推导，说明推导依据，不作为已确认需求。
- **待确认**：资料缺失、矛盾或无法确定。表述为“已读资料未说明”，不能直接认定系统没有该能力。
- 示例企业和数字应注明教学假设，不能编造真实业务事实。
- PRD 与原型冲突时并列给出两处描述，不默认某一方正确；用户或项目已规定优先级时按约定分析，并指出需同步修正之处。
- 只有实际阅读的资料才能列入分析依据；无法访问、版本不明或未读部分写入分析限制，不虚构引用。

## 怎样解释每个模块

- 用一句话说明“谁在什么场景，通过本模块处理什么事，获得什么结果”。
- 结合贯穿案例解释前置条件和业务动机，再按操作顺序写用户动作、系统处理、成功／失败结果及下一步。
- 抽取影响业务的关键数据，不抄全量字段字典。说明数据来源、筛选范围、计算用途和输出去向；需要人工输入时指出由谁、何时输入。
- 陌生业务术语在首次出现处用一句白话解释，复杂术语只解释到能读懂当前流程，不将文档变成大词典。
- 整体业务必须有流程图。复杂模块另画关键分支；表格已足够说明的简单模块不重复画图。图中对推测或缺失步骤显式标注。
- 有计算时给出输入、公式、中间值和结果，核对单位、比例、精度、时间边界和数量平衡；公式未定时不制造确定结果。

## 功能分析：把每个按钮和选项讲明白

读者看不懂的往往不是整个模块，而是单个功能。对模块内每个功能入口（按钮、开关、下拉选项、批量操作、页签）逐项做功能分析，用大白话回答四件事：

1. **干什么用**：一句话业务目的，回答“什么场景下会用到它”。
2. **怎么用**：前置条件（例如必须先保存表头）、操作对象（当前行／勾选多条／全部数据）。
3. **点击后系统做了什么**：按什么条件取数、做什么校验或处理、写到哪；有明确筛选条件时逐条列出。配置类选项（如选择计算口径）要说明“选不同值时，后续哪个环节的结果会不一样”。
4. **带来了什么变化**：列表、状态、明细、下游模块各有什么影响；成功和失败分别是什么结果，下一步能做什么。

写法上：简单功能可用表格逐行列出；含义抽象或带取数逻辑的功能（如“同步”“自动提取”“按口径计算”）用“功能名＋四个问题”的段落展开，必要时配一张小流程图。资料只给按钮名、没有处理逻辑时，按“输出的证据边界”标注待确认，不自行编造规则——功能分析和后文“按钮规则审查”配合使用：前者负责让读者看懂，后者负责发现规则缺口。

## 重点审查维度

按实际业务选择检查项，不把所有模块强制套成同一套复杂工作流。

| 维度 | 核查重点 |
| --- | --- |
| 职责与范围 | 模块解决什么问题；入口是否存在；本期范围与流程依赖是否匹配 |
| 按钮与规则 | 前置状态、操作对象／范围、处理依据、通过标准、成功结果、失败提示、下一步限制是否明确 |
| 数据与计算 | 来源、筛选条件、关联依据、时间范围、公式、计量单位、零值／空值及结果映射是否衔接 |
| 状态与角色 | 状态由谁或什么事件产生；允许的操作；审核、撤回、修改、作废等实际分支是否闭环 |
| 跨模块衔接 | 上游能否产生下游所需数据及状态；何时传递；返回结果；上下游修改后的影响 |
| 重复与异常 | 相关场景中的空数据、重复提交／计算／同步、失败重试、部分成功、上游修改／删除如何处理 |
| 文档一致性 | 同一概念、字段、公式、状态、版本范围在 PRD 不同位置及原型间是否一致 |
| 可验收性 | 是否能仅凭资料判断给定输入与操作应得到什么结果；示例能否按规则复算 |

### 特别关注：只有按钮名，没有规则

资料写“点击校验”不等于校验规则完整。先在其他章节、弹窗和关联说明中查找，再核查：

- 校验哪条、哪些已选数据，还是整个业务单据？
- 校验哪些字段、数据关系或业务条件，依据什么标准？
- 何时允许校验；通过和不通过各产生什么结果？
- 错误怎样展示及定位，用户怎样修正？
- 不通过是否阻止保存、提交或其他下一步操作？修改后是否需要重新校验？

缺失时具体指出“缺哪项、为什么影响操作或验收”，不要只复述“执行校验”，也不编造规则。查询、保存、计算、生成、审核、同步、导入、删除等按钮采用相同的输入—规则—输出思路，按实际风险判断需要追问的细节。

## 问题清单的质量

- 每个问题使用稳定编号 Q01、Q02……；模块内引用编号，完整内容只放统一问题表，避免重复。
- 类型可用：范围不清、概念不清、规则缺失、前后矛盾、数据断点、状态断点、异常遗漏、PRD 与原型不一致。
- 写清资料位置和具体描述；矛盾需列出两边内容；解释影响，给出能明确回答的问题，必要时附候选方案。建议不能伪装成产品结论。
- 优先级：**阻断**＝无法确定主流程、关键计算或验收结果；**重要**＝主线可理解但关键分支或处理未定；**一般**＝不影响主线的文字、展示、交互细节。
- 区别真正矛盾、术语不同但含义相同、教学示例简化和未说明。不要为了凑数量制造问题，也不把每个缺少技术实现细节的地方列成需求缺陷。
- 将阻断主线的问题放在前面；确认一处规则是否已能解决多个表面问题，避免拆成重复提问。

## 交付与复核

用户要求保存时写入指定 Markdown；没有目标文件时按当前任务提供文档内容，只有用户要求落盘且位置无法确定时再询问。已有分析只更新相关范围，保留用户修改，不自动改动 PRD、原型或代码。

完成前检查模块覆盖、主线案例和流程图是否一致，逐模块是否能回答“什么时候用、怎么操作、系统做什么、结果去哪”，问题是否有依据且可回答。核对案例数字、引用、表格与图表语法。区分已检查与未检查内容，不将文档自洽当成实现通过验证。

交付时给出结果文件或完整分析，简述已覆盖范围、关键阻断问题和实际限制，不只返回一份问题清单。
