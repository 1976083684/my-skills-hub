# PRD 模板占位符与填写规则

## 1. 通用占位符规则

模板中的方括号内容 `[说明文字]` 是占位符，不是最终 PRD 正文。生成实际 PRD 时必须按以下规则处理：

1. **已知信息**：从用户输入、附件或已确认资料中提取，替换占位符。
2. **未知但非关键的信息**：不猜测；删除无关项，或在适当章节标记“待确认”。
3. **缺失且影响业务判断的信息**：列入“待确认事项”，说明影响；确有必要时先向用户提问。
4. **不适用的章节**：删除整节或标注“不适用”并说明原因，不保留空表格。
5. **不能将示例当成事实**：例如 P0/P1/P2、V1.0、目标值、日期均为示例或占位值，除非用户确认，否则不得当成项目事实。
6. **禁止无意义占位**：最终交付的实际 PRD 不应残留 `[功能名称]`、`[说明]` 等未处理占位符；模板交付本身除外。

## 2. 占位符字典

| 占位符/字段 | 应填写的内容 | 信息来源 | 缺失时的处理 |
|---|---|---|---|
| `[产品或系统名称]` | 产品、系统或业务平台的正式名称 | 用户描述、现有文档 | 可暂写“待确认”或删除 |
| `[需求名称]` | 简短、可识别的需求标题 | 用户需求 | 根据已知内容拟定；避免夸大范围 |
| `[需求编号]` | 团队规定的唯一编号 | 需求管理系统/用户提供 | 无编号规则时删除或待分配，不自行发明正式编号 |
| `[负责人]` | 产品、业务或交付责任人 | 用户提供 | 写“待分配”或删除 |
| `[版本号]` | 文档版本 | 版本管理约定 | 新建初稿可用 V1.0 作为文档版本示例，但需标明草稿；无版本管理要求时可删除 |
| `[文档状态]` | 草稿、评审中、已确认、已发布等 | 当前实际状态 | 依据当前阶段填写，不得标记为已确认除非确已确认 |
| `[计划时间]` | 需求、评审或上线时间 | 用户/项目计划 | 未确认写“待确认”，不推测日期 |
| `[背景/现状]` | 需求产生原因、现有流程及痛点 | 用户描述、现有资料 | 用已知事实描述；信息不足列待确认 |
| `[问题及影响]` | 当前可观察的问题及其业务影响 | 用户描述、数据或调研 | 不编造损失、比例或用户反馈 |
| `[目标]` | 需求完成后期望实现的变化 | 用户明确目标或共同确认 | 目标不明确时提出澄清或列待确认 |
| `[成功指标]` | 衡量目标是否达成的指标 | 业务数据、产品决策 | 不凭空设数值；没有量化指标时可用可验证的定性目标 |
| `[当前基线]` | 指标现状 | 现有数据 | 写“暂无数据/待确认” |
| `[目标值]` | 预期指标目标 | 业务确认、实验结果 | 写“待确认”，不得自行给出行业数字 |
| `[统计口径/周期]` | 指标计算方式、时间窗口、适用范围 | 业务规则/数据定义 | 待确认 |
| `[用户或角色]` | 使用功能的人或系统角色 | 业务场景、权限资料 | 根据已知场景列出；不确定的角色列待确认 |
| `[使用目的]` | 用户要完成的任务 | 业务需求 | 依据场景概括，不添加未经证实的目的 |
| `[本期包含]` | 本次交付明确包含的功能 | 需求范围确认 | 不明确的功能不要默认纳入，列待确认 |
| `[本期不包含]` | 明确排除的功能或延期项 | 范围讨论 | 若无明确排除项可删除，但需避免让范围产生歧义 |
| `[触发条件]` | 用户操作、系统事件、时间或业务条件 | 业务流程 | 缺失且影响流程时列待确认 |
| `[前置条件]` | 执行操作前必须满足的状态、权限或数据条件 | 业务规则 | 不猜测；必要时提问 |
| `[功能名称]` | 功能标题，建议使用“动作 + 对象”或清晰业务名词 | 需求内容 | 从已知需求中归纳 |
| `[功能目的]` | 功能解决的问题或支持的业务目标 | 需求背景 | 与目标章节保持一致 |
| `[用户操作]` | 用户或调用方执行的动作 | 流程、原型 | 未提供原型时可描述已知操作，不虚构页面细节 |
| `[系统行为]` | 操作触发后系统应执行或返回的行为 | 业务规则 | 必须明确到可验证程度；未知内容列待确认 |
| `[业务规则]` | 条件、限制、计算、优先级及结果 | 业务确认 | 不将常见做法当作当前项目规则 |
| `[输入]` | 输入内容、字段、来源、格式和限制 | 需求或接口资料 | 仅列已知信息，缺失项待确认 |
| `[输出]` | 页面结果、业务结果、响应或状态变化 | 需求或接口资料 | 不虚构字段和返回结构 |
| `[异常条件]` | 失败、非法输入、冲突、超时等场景 | 风险分析、业务规则 | 覆盖重要场景；无法确定的处理方式列待确认 |
| `[优先级]` | 团队约定的需求优先级 | 产品/项目确认 | 采用团队既有规则；若没有，先约定，不强制套用 P0/P1/P2 |
| `[页面/区域]` | 页面、弹窗、列表或操作区域 | 原型/需求 | 无 UI 的后台或接口需求可删除该节 |
| `[权限/责任]` | 角色可执行操作及数据范围 | 权限规则 | 不确定时列待确认 |
| `[状态]` | 业务对象的状态名称或编码 | 已确认状态定义 | 不擅自发明状态枚举 |
| `[数据/约束]` | 字段、数量、金额、精度、唯一性等业务约束 | 业务规则/数据定义 | 不明确的计算口径列待确认 |
| `[验证方式]` | 功能测试、接口验证、压测、审计检查等 | 验收要求 | 选择能验证该要求的方法 |
| `[验收编号]` | 验收条件的唯一标识 | 文档编号规则 | 可采用 AC-001 等局部编号；若已有编号规范则遵循现有规范 |
| `[预期结果]` | 操作后可以观察、判断的结果 | 业务规则、产品决策 | 不使用“正常处理”等模糊表述 |
| `[依赖]` | 外部系统、团队、数据、审批或环境依赖 | 项目资料 | 无依赖时删除该项 |
| `[风险]` | 可能影响交付、正确性、安全或运行的风险 | 需求分析 | 不夸大风险；说明影响及应对方式 |
| `[待确认问题]` | 尚未有结论且影响需求的问题 | 需求分析 | 每个问题尽可能关联影响、负责人和计划时间 |
| `[发布日期/灰度/回滚]` | 已确认的发布要求 | 发布计划 | 尚未制定时写待确认或删除该节 |
| `[版本/日期/确认人]` | 文档变更历史 | 评审记录 | 初稿可留空表头；没有版本治理需求时可删除 |

## 3. 复杂度与章节启用规则

### 简单需求
保留：文档信息、背景/目标、范围、功能需求、必要规则、验收标准、待确认事项。
可合并：用户场景与背景、流程与功能步骤、异常与验收。
可删除：无页面的交互章节、无明确要求的非功能章节、无发布安排时的发布章节。

### 一般需求
保留通用基础章节；根据实际情况补充权限、状态、数据和异常规则。

### 复杂业务需求
按需补充：
- 业务术语与角色职责；
- 端到端流程及跨系统边界；
- 单据/业务对象关系；
- 状态流转与操作限制；
- 数量、金额、单位换算和累计规则；
- 重复操作、撤销、部分执行、冲销和补偿；
- 对账、审计、迁移和上线切换。

这些章节不是因“供应链”或其他行业标签而自动启用，而是由需求本身的复杂度决定。

### 技术产品需求
在通用模板基础上按需补充：
- 使用方和能力清单；
- 输入输出契约；
- API/事件的业务语义；
- 幂等、重试、超时、兼容性等产品级约束；
- 性能、可靠性、安全与可观测性目标。

具体数据库设计、模块结构、实现方案及技术选型放入技术设计文档。

### AI 功能需求
在通用模板基础上按需补充：
- 输入输出与能力边界；
- 事实依据、知识来源和数据权限；
- 输出质量评估与验收门槛；
- 无答案、低质量输出、拒答和模型不可用时的处理；
- 人工审核、隐私、安全、成本和延迟要求。

普通非 AI 需求不应包含这些 AI 专项章节。

## 4. 生成最终 PRD 前的占位符检查

- [ ] 所有占位符已替换、删除或明确标记待确认。
- [ ] 未将示例值当成已确认事实。
- [ ] 未编造业务指标、时间、字段、状态或规则。
- [ ] 不适用章节已删除或合并。
- [ ] 每个核心功能有可理解的系统行为。
- [ ] 核心验收条件可执行、可判断。
- [ ] 待确认问题已集中列出，并说明影响。
