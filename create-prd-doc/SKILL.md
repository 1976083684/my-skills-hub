# 标准 PRD 编写 Skill

## 目标

将用户提供的想法、需求描述、会议纪要或现有产品资料，整理成标准、可执行的产品需求文档（PRD）。优先采用通用 PRD 基础结构，再根据需求类型、复杂度和风险选择性补充章节。

## 核心原则

1. **先判断需求，再选择章节。** 不要求所有场景机械地填写全部章节。
2. **基础结构稳定，扩展内容按需启用。** 普通需求保持简洁；复杂业务补充流程、规则、状态、关联关系等。
3. **不虚构事实。** 不得自行编造业务规则、接口字段、数据指标、合规要求、时间计划或已确认结论。
4. **区分事实、假设与待确认项。** 用户明确提供的内容标为已知事实；合理但未确认的内容标为假设；缺少且影响方案的内容列为待确认。
5. **产品需求与技术实现分离。** PRD 重点描述业务目标、用户场景、功能行为、业务规则和验收条件。数据库表、类结构、设计模式、事务实现、具体中间件配置等原则上属于技术设计文档；如果用户明确提出技术约束，可在 PRD 中记录约束及原因。
6. **写清可验证的行为。** 避免“体验良好”“性能高”“操作方便”等无法验收的空泛描述。能量化时写明指标、条件和验证方式；未知时标记待确认，不擅自设值。
7. **避免重复和过度设计。** 每个章节只保留与当前需求相关的信息。不要为了模板完整而填充无意义内容。
8. **尊重原始资料。** 用户提供 PRD、原型、流程图或已有规则时，优先沿用并整合，不随意改写已确认的业务含义。
9. **发现冲突先显式指出。** 对不同材料中的规则冲突、定义不一致或前后矛盾，列出冲突和影响；不要自行选择一方当成事实。
10. **输出面向协作。** 文档应让产品、开发、测试及相关业务人员能够理解需求范围、系统预期行为和验收标准。

## 适用范围与边界

### 适用场景

- 常规业务系统、管理后台、查询/新增/编辑/删除、导入/导出、审批等功能。
- 业务流程、权限、状态、报表和数据维护功能。
- 供应链、工业互联网、贸易、仓储、报关、物流等复杂业务需求。
- 技术平台或集成能力的“产品需求”部分，例如对外提供什么能力、谁使用、输入输出契约和服务目标。
- 从一个想法、需求描述、会议纪要或旧版 PRD 形成或完善 PRD。
- 对已有 PRD 进行结构化、补全、检查和精简。

### 不应直接用 PRD 替代的文档

- 技术架构、模块拆分、数据库表结构与索引、Java 类设计、事务边界、MQ 可靠投递实现、具体算法实现：使用技术设计文档。
- 测试策略、测试计划、完整测试用例：使用测试文档；PRD 中保留验收标准和关键场景。
- 纯 UI 视觉规范：使用 UI/交互设计规范；PRD 记录与业务有关的交互行为。
- 纯项目排期、资源计划、研发任务拆分：使用项目计划或任务管理文档。
- AI 模型的系统提示词、评估集实现细节、模型路由实现等：属于 AI/技术设计细节；PRD 只描述产品行为、质量目标、失败兜底和验收要求。

### 不同复杂度的使用规则

- **简单需求**：保留文档信息、背景/目标、范围、功能需求、必要规则、验收标准、待确认项。可合并章节。
- **一般需求**：使用完整基础模板，明确场景、功能行为、权限/数据、异常及验收。
- **复杂业务需求**：在基础模板上按需补充端到端流程、业务术语、角色职责、单据关联、状态流转、数量/金额规则、跨系统交互、对账、异常恢复等。
- **高风险或多系统需求**：进一步明确数据权限、审计、合规、兼容性、迁移、灰度、回滚、监控及业务连续性。
- **技术产品需求**：保留通用 PRD 的目标、使用方、能力、输入输出、限制和验收；增加接口/事件契约、数据语义、性能与可靠性目标。具体技术实现另写技术设计。
- **AI 功能需求**：在基础模板上按需补充输入输出、模型能力边界、知识来源、质量评估、幻觉/无答案处理、人工兜底、隐私、安全、成本与延迟等；不把所有 AI 专项章节强加给普通功能。

## 执行流程

### 第一步：识别输入类型

判断用户输入属于哪种情况：

- 只有想法或问题描述；
- 已有明确需求说明；
- 已有 PRD，需要整理或完善；
- 有原型、流程图、表格或其他附件；
- 用户要求生成技术设计、测试文档等非 PRD 产物。

若用户明确要技术设计或测试文档，不要把产物强行改成 PRD。可以指出文档类型，并按用户要求处理。

### 第二步：判断是否缺少关键资料

优先判断以下信息是否足以继续：

- 要解决的问题或业务目标；
- 主要用户/使用方；
- 核心业务场景；
- 本期范围；
- 关键业务规则或系统预期行为。

如果缺少的信息会实质改变需求，且无法安全地用待确认项表达，只问最关键的一到两个问题。不要一次抛出长问卷。
如果可以先产出有价值的初稿，则继续撰写，并将缺失信息集中放入“待确认事项”，不因非关键缺项阻塞输出。

### 第三步：确定模板深度

按复杂度、风险和协作范围决定保留哪些章节。不得只根据行业名称决定文档长度。例如，供应链系统中的简单查询功能可以使用简版；一个普通管理系统中的跨组织审批也可能需要复杂流程扩展。

### 第四步：组织需求

- 将目标与功能需求分开。
- 将用户操作与系统行为分开。
- 将业务规则与页面展示分开。
- 将正常流程与异常/边界场景分开。
- 将验收条件写成可观察、可验证的结果。
- 将需求事实、假设和待确认问题分别标识。
- 对复杂规则使用表格；简单规则优先使用短列表。

### 第五步：检查完整性与一致性

输出前检查：

- 需求范围与功能清单是否一致；
- 每个核心功能是否说明触发条件、处理行为和结果；
- 关键业务规则是否明确；
- 权限、状态、数据边界及异常处理是否适用且已覆盖；
- 验收标准是否可执行、可判断；
- 是否把技术实现细节误放进 PRD；
- 是否有未经用户确认的假设被写成事实；
- 是否有重复章节、空泛要求或无意义占位内容。

### 第六步：输出

- 默认使用 Markdown。
- 先给出可直接使用的 PRD 正文；不要先长篇解释模板理论。
- 用户要求模板时，输出可复用的空白模板，并附占位符说明。
- 用户要求根据具体需求生成 PRD 时，替换占位符为已知内容；未知内容标为“待确认”，不要留下大量模板说明。
- 如用户要求文件或打包，生成相应文件，并确认实际文件路径后再提供链接。

## 通用 PRD 基础结构

按需保留以下章节，不适用的章节可以删除或合并。

1. 文档信息
2. 需求背景与问题
3. 建设目标与成功指标
4. 用户/使用方与使用场景
5. 需求范围（本期范围、非目标）
6. 业务流程/用户操作流程
7. 功能需求与业务规则
8. 页面与交互要求（适用时）
9. 数据、权限与状态（适用时）
10. 异常场景与边界条件
11. 非功能要求（有明确要求时）
12. 验收标准
13. 依赖、风险与待确认事项
14. 发布与上线要求（适用时）
15. 版本与变更记录（需要追踪时）

详细模板见 [references/prd-template.md](references/prd-template.md)。
占位符、缺省值和删减规则见 [references/placeholder-guide.md](references/placeholder-guide.md)。

## 禁止事项

- 不声称存在适用于所有企业的唯一 PRD 行业标准。
- 不因“大厂/中小厂”或某个行业标签而机械决定章节。
- 不把 PRD 写成技术设计文档、测试计划或项目排期表。
- 不把未知信息自行补成确定事实。
- 不用“系统正常处理”“保证稳定”等模糊句子代替具体行为或验收条件。
- 不为追求文档完整而重复同一规则。
- 不要求用户回答所有可选问题后才开始；可先生成合理初稿并列出待确认项。
