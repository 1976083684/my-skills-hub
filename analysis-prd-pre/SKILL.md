# PRD 评审前对齐分析

## 目标

在 PRD 评审会之前，把 PRD + 原型逐模块对齐一遍：先用「功能预览」还原这个模块用户能做什么，再用「逐功能评审」指出每个功能是否合理、遗漏、有争议，产出一份可以直接拿去评审会逐条确认的对齐文档（Markdown）。

默认简体中文。正文一律用嵌套列表组织，不用大段表格（仅文档开头信息栏用表格）。

## 输入与范围

1. 确认分析对象：PRD 文件、原型文件、附件模板（导入模板等）；确认分析范围（哪几个模块/章节），不自行扩展到范围外模块。
2. 确认输出位置与文件名：默认保存在 PRD 同目录，命名形如《【PRD】<主题><期次>对齐.md》；用户指定时从用户。
3. 若用户提供代码仓库，可追加一步「现状核对」：确认该模块当前是否已实现/预留接口/完全缺失，写入评审对应小节；未提供仓库则不写现状，不臆测。

## 执行流程

1. **通读 PRD**：长文分段读完全部目标章节，建立模块清单（模块名 + PRD 章节号）。注意被删除线划掉的内容也要记录（常与原型/其他章节冲突）。
2. **提取原型**：原型多为 HTML。用 scripts/extract_html_text.py 按章节提取纯文本（自动处理编码与标签剥离），逐模块与 PRD 对照；原型中的行级操作、弹窗、默认文案、演示数据都要看。
3. **逐模块对照**：对每模块核对——页面结构（主从层级、页签、入口按钮）、每个功能按钮、每个字段（必填/带出/置灰/联动）、导入导出、状态机、与上下游模块的取数关系。
4. **（可选）现状核对**：在代码仓库搜索模块关键词（中文+英文+表名），确认实现现状与预留坑位（接口、空实现、已建表），注明文件位置。
5. **按模板输出**：每个模块严格两段式，模板见 references/output-template.md；评审检查清单见 references/review-checklist.md。
6. **结尾汇总**：跨模块关键问题单独成章，按"必须先闭环（❌）"和"待确认（⚠️）"分组，每条一句话说清影响和涉及章节。

## 输出硬规则

- 开头信息栏用表格：对齐范围 / 依据资料（含版本日期）/ 标记说明 / 整理日期。
- 评审标记口径：
  - ✅ 合理可开发：规则完整、可直接落地
  - ⚠️ 遗漏或不完整需补充：PRD 缺失但可推断，或只有原型有
  - ❌ 矛盾或硬伤需产品确认：PRD 内部矛盾、PRD 与原型冲突、流程断裂、取数口径缺失
- 每条评审必须带出处：【PRD x.x】/【原型】/【PRD x.x vs 原型】。
- PRD 与原型冲突时**并列两处描述并给建议采信方**，不默认某一方正确（用户已约定优先级时按约定）。
- 反推的内容（如导入列清单）必须标注"反推/推断"，不得写成 PRD 已有。
- 只写影响开发落地的问题；纯文档排版/章节编号错乱类问题**不写**。
- 功能预览写"用户能做什么"，不复述 PRD 原文表格；逐功能评审按功能逐项走（查询/新增/修改/删除/查看/导入/导出/明细维护/DB建表/与下游关联），没有的功能项不硬凑。
- DB 建表评估每模块必写：是否需新增表、建议几张（主/从）、字段是否都有出处、缺的是字段还是行为规则。
